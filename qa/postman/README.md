# QA Commerce Lab - Registration Postman Setup

## Import

Import these two files into Postman:

1. `QA-Commerce-Lab-Registration.postman_collection.json`
2. `QA-Commerce-Lab-Local.postman_environment.json`

Select the environment:

`QA Commerce Lab - Local`

## Runtime URLs

```text
Backend API: http://localhost:3000
Health:      http://localhost:3000/health
Mailpit:     http://localhost:8025
PostgreSQL:  localhost:5432
Redis:       localhost:6379
```

## Execution Order

Run:

```text
00 - Environment Check
01 - Registration Normal Suite
```

The first positive Registration request generates a unique `registration_email` and saves it in the active Postman environment. The next two duplicate-email requests depend on that value, so keep the normal suite order.

The normal suite contains the positive flow, required-field validation, Arabic/English name rules, allowed/unsupported name characters, name boundaries, invalid email, password policy/boundaries, case-insensitive duplicate protection, privileged-field rejection, and malformed JSON.

## Manual Fault Injection

Do not include `99 - Manual Fault Injection` in the normal runner execution.

That request validates the documented `503 EMAIL_DELIVERY_FAILED` behavior. The backend must already be running, then Mailpit is deliberately stopped before sending that single request. Mailpit is started again immediately afterward.

## Evidence After Execution

Use Mailpit to inspect the verification email generated by successful Registration requests.

Use:

`qa/sql/registration-validation.sql`

to validate the PostgreSQL state after the Postman run. Replace `PASTE_REGISTRATION_EMAIL_HERE` with the `registration_email` value generated by Postman.

Do not expose plaintext passwords, password hashes, raw verification tokens, or token hashes in screenshots or defect evidence.
